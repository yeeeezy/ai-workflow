## User scope correction

This is **not limited to humanoid ground waypoints**. The user wants the random destination search, route validation and patrol flow unified for ground, wall-crawling and flying enemies. A common patrol contract should cover selection, request ownership, movement completion, retry and interruption. The actual candidate geometry, reachability and movement executor remain specific to ground, wall and air.

## Current implementation

- Ground: `FEnemyGroundPointQuery` and shared ground BT tasks handle NavMesh reachability and request-owned movement for combat consumers. Humanoid waypoint patrol uses that reachability query but `AHumanoidEnemy` still owns its own `MoveTo`, turn, arrival and wait sequence. Random ground roaming is not implemented as a common patrol selector.
- Wall: VoidGazer Ambient uses `FEnemyWallPointQuery` and `UWallCrawlMovementComponent` for bounded planar point selection and movement. Wall transfers are separate GAS actions. Complex routing around holes/corners is not implemented.
- Air: CoreMorph Ambient runs `UGA_CoreMorphFlight` and `UCoreMorphFlightComponent` on an assigned spline or authored orbit/dive. It has no generic random three-dimensional point query, obstacle-aware path planner or reusable air patrol request protocol.
- Medusa has ground combat approach/retreat adapters but no Ambient patrol. Existing route choreography and per-creature animation must be preserved.

## Planned design and acceptance

1. Define one Ambient patrol orchestration contract: choose a random or authored candidate, validate a reachable route, start an owned movement request, observe arrival/failure, wait/retry as configured, and cancel only the owned request on branch abort, death or unpossess.
2. Ground provider uses NavMesh and shared ground point/reachability functions, including bounded random roaming. Wall provider uses surface context, support and capsule clearance; preserve current Void crawl/leap behavior. Air provider chooses volumetric points and validates an actual traversable route or reports failure; an authored spline may be a route source but is not itself general pathfinding.
3. Reuse the existing ground, wall and flight executors where their movement rules apply. Do not substitute a universal XYZ-only solver for the three movement types. Keep enemy-specific turn, wait, animation, gait, attack and encounter policy outside the generic query and request lifecycle.
4. Cold-load affected behavior trees/Blueprints. In PIE verify each movement type's random destination selection, valid arrival, blocked/unreachable handling, bounded retry, target/lifecycle interruption, death and unpossess cleanup. Preserve Humanoid waypoint order and search recovery, VoidGazer wall patrol/transfers, and CoreMorph authored flight/encounter choreography.
5. After implementation and verification, update `arch/15-enemy-movement.md` and the relevant new-enemy guidance in `arch/11-enemy-ai.md` to describe the actual shared point selection, path validation, patrol request contract and ground/wall/air providers. Documentation is required for completion.

### Initial proposal (ground implementation supersedes the first two items below)

1. Add one native `IEnemyPatrolProvider` contract and a shared Ambient BT task that owns the state sequence `Select → Validate → Move → Arrive/Wait → Retry/Fail`. The task stores a request token, deadline and bounded retry state; each provider stores its medium-specific route. Abort/death/unpossess cancel only the matching token so a newer combat or encounter action is never stopped. Engagement remains the sole lifecycle authority.
2. Ground provider: extend `FEnemyGroundPointQuery` with bounded random NavMesh destinations and reuse its non-partial `Reachable` check; use AI `MoveTo`/PathFollowing/CharacterMovement as the executor. The Humanoid adapter keeps authored patrol index order and its turn, scan and wait presentation; random roaming is used when configured instead of authored points. The provider maps the shared token to its `FAIRequestID`.
3. Wall provider: reuse `FEnemyWallPointQuery`, `CanMoveTo` support/capsule validation and `WallCrawlMovementComponent::RequestMove`; the token identifies the crawl request. Invalid support/obstacle reports failure and bounded retry. Existing GAS wall transfers and ground return remain distinct actions; no unvalidated corner/hole routing is claimed.
4. Air provider: add a bounded three-dimensional random-goal and route query with collision clearance sweeps, altitude bounds and a finite waypoint search. It returns a route or explicit failure, not a straight-line movement through obstacles. Feed the route into CoreMorph's existing `FlightComponent`/`FlightMotion` through the flight GA. Keep its current spline/reference choreography as an authored route mode; on encounter activation hand the live body pose/velocity to the existing approach before cancelling the old patrol token. Closed splines report lap completion for the common lifecycle without resetting presentation.
5. Preserve family-specific turn, dwell animation, gait, skill and encounter policy behind provider hooks. Cold-load affected BT/Blueprint assets and run actual PIE cases for each medium: random/authored destination, valid arrival, obstacle/unreachable, retry cap, branch abort, death and unpossess, plus legacy waypoint order, Void leap and CoreMorph encounter handoff. Update `arch/15-enemy-movement.md` and `arch/11-enemy-ai.md` with the implemented contract before closing FEAT-284.
